# Resumable provisional development pilot

This run uses all twenty previously selected and versioned development cases,
with four workflows per case. Each age 13–17 contributes four cases. The private
selection contains ten feasible-intent, four missing-information, three conflict
and three outside-scope drafts; six contain factual food questions. These are
provisional development categories, not accepted final gold labels or certified
feasibility claims. Private selection/review metadata stays outside model inputs.
Some cases already appeared in the preceding smoke tests under earlier settings.
Retain that development exposure; this is not a fresh held-out population.

The overall configuration and all eighty job identities are fixed before the
first model call. Preserve pilot_index and scheduled_index for case order and
position_in_case for the prepared balanced workflow order. CSV hashes identify
the original version-1 public records. The version-2 records differ only by the
previously recorded fictional schedule-coverage authoring amendment; keep both
lineages rather than treating their different hashes as corruption.

The operational runtime from Step 31-9 supplies the common bounded final
contracts and reversible reference representation. Planner 1 receives no
reference packet. Versions 2–4 retain complete matching reference content and
all qualifications. The independent food audit excludes exact question echoes
from numeric-claim assessment without editing model replies. The remaining
calendar, commitment, resource, scope and fact checks stay required as declared.

Model, generation options, context and output reserves, safety margin, complete
backend-rendered prompt checks and two-revision V4 policy remain unchanged. The
maximum is fifteen generation submissions per case and three hundred across the
pilot; this is a conservative ceiling, not an expected number or a cost quote.
All native transport attempts, reference work, role timing and cached observations
remain recorded. No automatic retries, output repair or best-of selection are
added. A fatal result never permits an earlier diagnostic draft as its substitute.

The default batch starts at most five incomplete cases. Completed cases and all
their evidence are verified before being skipped. Rerun the same cell to advance
through the remaining cases. Exact saved jobs are reused after a conclusive
interruption. An uncertain request, incomplete reference preparation or changed
dependency stops progress for review. Do not delete locks or request markers to
force another submission.

A case with four terminal model outcomes, complete matched reference preparation
and completed independent checks is recorded even when a planner failed, refused
inappropriately, omitted an answer or retained required unknowns. Failed reference
preparation and uncertain backend outcomes leave the case incomplete and stop
the batch. They are not skipped to improve the recorded outcome distribution.
Count cumulative submissions from the saved traces without charging reused jobs
twice. The initial batch begins mostly with age 13 and is not representative of
the entire pilot.

The cell reports concise case progress and saves the full records. A five-case
batch may take several minutes, depending on reference startup and V4 revisions.
Run it once, wait for it to finish, then rerun the same cell when ready. Four
completed five-case batches cover the twenty-case roster; a blocked batch may
need review before continuing. An operating-system batch lock prevents two
executions advancing the same queue simultaneously and releases on process exit.
The existing backend uncertainty markers remain authoritative after a crash.

This is development measurement with failures preserved. It does not produce
final study scores, select a winning planner, accept study cases, invent human
ratings, activate app generation or freeze the final protocol. Full results and
coverage should guide the remaining scoring preparation and final settings.
