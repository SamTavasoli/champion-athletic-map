# Request-specific response requirements

The saved Step 31-6 job outcomes match their independent assessment hashes and
sealed job records. All four final replies genuinely omit the requested food
answer. The three reference-supported versions received the same frozen packet,
which contains the requested food record. V3 and V4 activated their food role,
but its contribution marked itself provided while leaving every content list
empty. Its 260-character rationale repeats basketball scheduling information.
This is an observed model failure accepted by a permissive structural contract,
not evidence that retrieval failed or that the output reserve was exhausted.

The new contract builder derives only structural requirements and planning-window
facts from public input. It reads no food lookup values, private expected answer,
catalog activity choice or model evaluation score. When a public food question
exists, every final response branch requires at least one nonempty food statement.
That statement may honestly explain that the information is unavailable. The native
property order places this field immediately after response_type. Numeric accuracy,
food-answer relevance and appropriate uncertainty still need independent assessment.

The food-role note has three complete object branches. A provided contribution
requires a recommendation; limited_information and outside_scope require an
unresolved issue. Nonempty irrelevant prose can still satisfy structure, so this
does not certify that a food note is useful or factually correct. The prospective
role adapter uses the same effective new schema for request generation and local
parsing. Training, recovery and evaluator output schemas remain unchanged.

The final native schema retains the original response branches and fixes the
planning-window scalar values from public input. Day dates are restricted to the
seven public dates. The local schema additionally enforces exact chronological
positions using the complete original day schemas. Backend chronology and unique
dates are not guaranteed by the native enum. Existing independent checks for
calendars, preserved commitments, root/component relationships, requested counts,
resources and facts remain necessary. A field-presence fix does not solve those
semantic failures.

Ollama documents JSON Schema in the format field. Its underlying grammar tooling
supports only a subset of JSON Schema and warns that unsupported features may be
silently skipped. We therefore keep prefixItems in local validation only; the
new native schemas still require an observed compatibility test on the actual
backend before any claim of enforcement or improved generation.

The new runtime composes isolated copies of the saved planners. It applies the
same final contract to all four clients and V4 revisions, changes the ambiguous
food-omission sentence only in their private in-memory adapter modules, and
retains V4's lossless candidate/check encoding. Food-only overrides apply to V3
and V4 drafting adapters. Model, output/context settings, acceptance rules, call
caps, complete request-budget checks and zero automatic retries remain unchanged.
The bound public input is checked before every request. New reference-policy
identities include ordered native-schema hashes and exclude measured setup times.

This checkpoint installs and tests the prospective contract and runtime, then
checks the saved failing replies under the new requirements without editing them.
Rejecting those replies is regression evidence for the contract, not evidence
that a future model reply will succeed. This cell does not construct a model
runtime, encode queries, call Ollama, modify the app gate, adopt final study cases,
freeze the protocol or replace the original independent-scoring parser. The
updated runtime will be used only by a separately recorded future experiment.
